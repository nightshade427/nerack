# Events, routines, tasks, and cron

- Events (`pubsub.h`) are durable. Names are global with one publisher each: `publish` declares the event and the keys it carries, `emit` fires it (only events the module publishes), and `subscribe` in any module names only the event. The keys are a contract checked at boot: `publish(.gives = {...})` lists what the event carries, `subscribe(..., .accepts = {...})` the keys the subscriber uses, each of which the publisher must give, and the subscriber starts with only those (none without `.accepts`). Removing or renaming a given key that a subscriber accepts fails the boot; adding one changes nothing. A queued event emitted by an older build that lacks an accepted key fails that delivery with `err_internal` naming the key, so ship a new given key before the subscribers that accept it. Delivery is asynchronous, after the emitting run (never inside it), and at least once: a crash replays undelivered events, so subscribers should be idempotent.
- A routine (`routine("name", {...})`) is a named group of steps that `run_routine("name")` runs inline, as if pasted into the caller: same context, so keys it sets are there for the caller's next steps. It never calls itself, directly or through another. Each key it reads must be settable at at least one `run_routine` site.
- A task (`task.h`: `task("name", {...}, .accepts = {...})`) is a durable background job; `queue_task("name")` queues it and the caller continues. It starts with only its `.accepts` keys, copied from the caller (none without `.accepts`), which keeps checkpoints small.
- `cron("name", "0 8 * * *", {...})` runs its steps as a task on a schedule, starting with an empty context (missed runs run once at boot; a run still going skips the next; instances sharing `task_db` on Postgres fire each run once). The name shows in logs and `nerack info`, and an override replaces a schedule by it. For one job on several schedules, put it in a routine and `run_routine` it from each `cron`.
- A task checkpoints context after each step and resumes after a crash (on the next boot, or within about 30 s on another instance sharing `task_db`/`pubsub_db`, which also replays undelivered events) at the step that was running, which runs again: each step runs at least once, so make outside effects idempotent (an `Idempotency-Key` header with a stable id). Finished steps never run again and their results stand; the rest runs with the app as deployed now (code, templates, SQL), and a step whose own code changed since counts as new and runs. Checkpoints keep strings, tables, and blobs; opaque values are dropped.
